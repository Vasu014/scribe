# Correctness audit — capture / transcription core

**Scope:** `Packages/MeetingKitCore/Sources/{CaptureKit,TranscribeKit}`, `SessionKit/{SessionCoordinator,TranscriptPipeline,SessionClock}`, plus the App wiring that instantiates them (`App/LazyWhisperKitTranscriber.swift`, `App/ScribeApp.swift`) and `Tools/SpikeHarness` results. Audited against SPEC §4.1/§4.2/§4.4/§4.6 and `docs/spikes/spike1.md`. READ-ONLY — no code changed.

## Verdict

The PCM/VAD/offset math and the recently-hardened stop path are in good shape: `TranscriptPipeline.finish(timeout:)`'s one-shot race is correct (both branches yield, the loser's yield lands on a dropped stream, the deadline task is cancelled, and the timeout path leaves the store consistent because the pipeline persists on every emission), the §4.2 one-inference-in-flight rule is genuinely enforced by `GatedEngine`'s async semaphore rather than merely intended, every `AsyncStream` continuation I traced is finished on all paths, and the Spike-1 smoke numbers confirm the gap-tolerance and buffer-cadence assumptions in `ChannelWorker` hold on real hardware (mic max gap 0.11 s against a 0.10 s + 0.05 s trigger; remote 0.03 s against 0.02 s + 0.05 s). The defects that remain cluster in *session-boundary interleaving* — the fix for the T10 stop hang opened a window in which `start()` is legal while a previous stop is still draining, and two pieces of state (`SessionCoordinator.pipelineStorage`, and `Resolver.sessionBuild` in the App) are still written on the assumption that only one session exists at a time. Finding #1 is the serious one: a Start clicked within the drain window produces a meeting that records audio into a `nil` pipeline and persists **zero** transcript segments, with no error anywhere. Two documented SPEC §4.1 behaviors (surface a warning on remote degradation; pause/resume capture across sleep/wake) are not implemented at all. None of findings #1–#5 is covered by the 82 passing tests.

**Counts:** 3 critical/major-confirmed, 12 findings total — 1 critical, 6 major, 5 minor; 6 confirmed, 4 likely, 2 speculative.

## Smells, not bugs

- `Packages/MeetingKitCore/Sources/SessionKit/TranscriptPipeline.swift:51` — both channel streams are `.unbounded` with no cap and no drop policy. Nothing observed exceeds a few MB (a stalled model for 20 s buffers ~2.5 MB across both channels), and §4.6 only forbids *disk*, but there is no ceiling if inference ever falls behind real time for a long stretch.
- `Packages/MeetingKitCore/Sources/SessionKit/TranscriptPipeline.swift:93-96` — the doc claims `LazyWhisperKitTranscriber` "FETCHES a ~500 MB Core ML model inside `transcribe(stream:)`". It does not: `WhisperKitConfig(download: false)` (`WhisperEngine.swift:57`) and `locateModelFolder` returning `nil` (`LazyWhisperKitTranscriber.swift:169`) make a missing model an immediate fallback. The stall is a *load*, not a fetch. Correct behavior, wrong rationale in a load-bearing comment.
- `SCKCaptureEngine.swift:113-115` claims the arrival-stamp error "is consistent across channels". Spike-1 data says otherwise: mic buffers are ~1600 samples (100 ms), SCK audio ~320 samples (20 ms), so `Me:` and `Them:` lines are skewed ~80 ms relative to each other. Irrelevant at Whisper granularity, but the comment is wrong.
- `PCMConversion.swift:187-199` — `flush()` allocates a fresh 4096-frame buffer per loop iteration and only exits on `frameLength == 0` or `.error`. Unbounded if a converter ever misbehaves. Never called by the engine (documented), so it is dead weight rather than a live risk. Also: the per-channel downsampler is discarded and rebuilt on format change (`SCKCaptureEngine.swift:498-504`) without a `flush()`, dropping the converter's held tail at each device switch — a few ms.
- `PCMConversion.swift:24-28` — a non-Float32 device format makes `monoSamples` return `[]` for every buffer forever, with no log and no degradation event. `accepts(format:)` (`PCMConversion.swift:121`) does not compare `commonFormat`, so no rebuild is triggered either. Unreachable today (AVAudioEngine taps and the SCK guard at `SCKCaptureEngine.swift:538-540` are both Float32-only), but it is a silent-death path on an unusual device.
- `SessionCoordinator.swift:654-666` — `EventBus.emit` holds an `NSLock` across `continuation.yield`. `AsyncStream.yield` does not run `onTermination` inline, so no deadlock today, but `remove(id)` re-acquiring the same non-recursive lock from `onTermination` is one API-behavior change away from one.
- `SCKCaptureEngine.swift:672-678` — `didStopWithError` spawns an untracked `Task { await handleRemoteFailure(...) }`. Nothing awaits or cancels it. A restart that lands after `stop()` and after a *new* `start()` passes the `stillRunning` check at `:421` and adopts a second SCStream into the new session (duplicate remote audio). Extremely narrow window; not worth a row on its own.
- `SessionCoordinator.swift:440-445` — `elapsed()` returns 0 for any phase other than `.recording`, so the menu-bar readout snaps to `00:00` during `.stopping`/`.processing` rather than freezing at the final value. Cosmetic, and deliberate per the `stop()` doc.
- Two-clocks rule (SPEC §4.1) is otherwise respected: every display path in `App/` uses `coordinator.elapsed()` or `endedAt − startedAt` (`HistoryWindowController.swift:1206`, `:1600`), and `nowOffset()` is used only for fragment anchors and device events. No violation found.
- §4.6 "raw audio never retained": confirmed clean. No file writes on any capture or transcription path; `WhisperEngine.swift:63-72` uses only the in-memory `transcribe(audioArray:)` entry point and documents why the `audioPath(s:)` overloads are avoided.

## Test coverage gaps

The package has 82 passing tests. **None of findings #1–#6 is covered**, and the shape of the gaps is itself a finding: every existing SessionKit test drives a single session to completion before the next assertion.

- **No two-session interleaving test at all.** `SessionCoordinatorTests.swift:235-529` never calls `start()` while a previous `stop()` or `retryFusion()` is in flight. Findings #1 and #2 both need exactly that: start during the drain (#1), start during a retry's fusion await (#2). A test injecting a slow `FusionRunner` and a slow transcriber and asserting that session B's segments land in the store — and that `displayState` stays `.recording` — would catch both.
- `testStopCompletesWhenTranscriptionStallsAndNeverDrains` (`:475`) is the only stall test and it asserts only that stop *returns*. It does not assert what the abandoned pipeline/transcriber does afterwards, which is where #5 lives. There is no test of `LazyWhisperKitTranscriber`/`Resolver` at all (it lives in `App/`, which has no test target).
- **No `CaptureEngine` tests beyond PCM math.** `CaptureKitTests/` contains only `PCMConversionTests.swift`; `SCKCaptureEngine.swift` (717 lines: start order, degradation ladder, restart counter, generation guard, device rebuild) has zero tests, by explicit design (`PCMConversion.swift:9-11`). Findings #6, #10 and #12 all sit in that untested surface. The degradation ladder and the generation guard are pure state machines and *could* be tested by extracting them from the SCK/AVAE objects; today only hardware runs exercise them.
- **No sleep/wake or interruption-recovery test.** `testDeviceChangeAndSleepWakeLoggedToDeviceEvents` (`:393`) asserts only that the three rows are appended — it cannot fail on finding #4 because the coordinator's contract is "log and relay" and there is nothing on the engine side to relay to.
- **No crash-recovery test for a session whose `endedAt` is null beyond the happy path.** `testCrashRecoveryMarksRecoveredAndOffersFusionWithoutRunningIt` (`:348`) covers `recording → processing + recovered`. Nothing covers a session left in `processing` with `endedAt == nil` by a crash *during* recovery: the next launch's scan (`SessionCoordinator.swift:156`) only looks at `.recording`, so such a row is never re-offered, and `HistoryWindowController.swift:1206` renders it with no duration forever. Correct-by-spec but untested and unasserted.
- **No `TranscriptPipeline.finish(timeout:)` unit test.** Its behavior is only exercised transitively through `stop()`. The timeout branch's post-conditions (consumers cancelled, `feed` a no-op, segments already persisted) are asserted nowhere directly.
- `EngineExclusivityTests.testBothChannelsNeverRunConcurrentInferences` (`:332`) does correctly cover the §4.2 one-in-flight rule — that guarantee is tested and holds.
